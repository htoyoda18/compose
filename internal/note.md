- desktop
  - Docker Desktop 統合
    - Docker Desktop アプリケーションとの通信・連携機能
  - `client.go` が Desktop 側のインメモリソケット(AF_UNIX/named pipe)に接続する `Client` を提供し、疎通確認 (`Ping`) や機能フラグ取得 (`FeatureFlags`) を行う
  - `proxy.go` の `Endpoint` は Docker Engine の情報から Desktop 統合用エンドポイントを解決する
- experimental
  - 実験的機能の管理
  - `COMPOSE_EXPERIMENTAL` 環境変数と Docker Desktop から取得した機能フラグを合成し、実験的機能ごとの有効/無効を表す `State` を提供する
  - 環境変数でグローバルに opt-out した場合や Desktop 非接続時は Desktop 側の状態取得をスキップする
- locker
  - ロック機構
    - 複数の Compose プロセスが同時実行されないように制御
  - `pidfile.go` がプロジェクトごとの PID ファイルを実行時ディレクトリ配下に作成し、多重起動を検出する
  - `runtime.go`/`runtime_*.go` が OS ごとに異なる実行時ディレクトリ(`XDG_RUNTIME_DIR` 等)の解決方法を吸収する
- memnet
  - メモリ内ネットワーク
  - `conn.go` の `DialEndpoint` が `unix://`/`npipe://` 形式のエンドポイント文字列を解釈し、対応するソケットへ接続する
  - OS ごとの実装 (`conn_unix.go`/`conn_windows.go`) が Unix ドメインソケットと Windows 名前付きパイプの差異を吸収する
- oci
  - Open Container Initiative 関連
  - `resolver.go` が docker/cli の認証情報を使ってレジストリ用の `Resolver` を構築し、マニフェスト/blob の取得・コピー・push を行う
  - `push.go` は compose.yaml や .env ファイルを OCI アーティファクトの layer として記述し、マニフェストを生成して push する（`docker compose publish` 等で利用）
- paths
  - パス処理ユーティリティ
  - `IsChild` が大小文字の違いやシンボリックリンクも考慮しつつ、あるパスが別のパスの子孫かどうかを判定する
  - `EncompassingPaths` が複数パスの集合から、それらをすべて包含する最小限のパス集合を求める（watch の監視対象パスの集約などで利用）
- pidfile
  - PID ファイルの読み書き
  - `pidfile.go` の `Read`/`Write` が指定パスの PID ファイルを読み書きし、既存ファイルが実行中プロセスの PID を指していればエラーを返す
  - `github.com/moby/moby/v2/pkg/pidfile` の暫定コピーで、`internal/locker` から OS 別の生存確認 (`alive`) 実装 (`pidfile_unix.go`/`pidfile_windows.go`) とあわせて多重起動防止に利用される
- registry
  - コンテナレジストリ関連
  - Docker Hub のデフォルトレジストリ名・ホスト名（`registry-1.docker.io` 等）を定数として定義する
  - `GetAuthConfigKey` がイメージ参照からレジストリ名を認証情報のキー（`docker.io` かどうかで index server の URL に正規化）に変換する
- sync
  - ファイル同期機能
  - `shared.go` がホスト側の変更パスとコンテナ側のパスを対応付ける `PathMapping` と、それを反映する `Syncer` インターフェースを定義する（`watch` 機能の同期処理で利用）
  - `tar.go` が変更されたファイル群を tar アーカイブとしてまとめ、コンテナへ転送する処理を担う
- tracing
  - 分散トレーシング機能
  - `tracing.go` の `InitTracing`/`InitProvider` が OTLP エクスポーター(gRPC)を構築し、コマンド実行全体を計装する tracer を初期化する
  - `docker_context.go` がアクティブな Docker コンテキストのメタデータから OTLP の接続先設定を自動検出し、`mux.go` は複数エクスポーターへの同時送出をまとめる
- variables.go
  - バージョン情報の管理
  - ビルド時に `-ldflags` 経由で注入される CLI のバージョン文字列 `Version` を保持する（未注入時は `"dev"`）
  - `main.go` のプラグインメタデータや `docker compose version` の出力に利用される

## 用語

- インメモリソケット / ソケット / Unix ドメインソケット
  - ソケット = プロセス同士が通信するための口(OS が提供するエンドポイントの抽象)。ポート番号と対立する概念ではなく、TCP ソケットの住所が「IP+ポート番号」で決まる、という包含関係
  - Unix ドメインソケットは TCP/IP を経由しないため**ポート番号を使わず**、代わりにファイルパス(`/var/run/docker.sock` 等)が住所になる同一ホスト内専用のもの
  - Docker Desktop はこれを「インメモリソケット」と呼び、接続先アドレスを `com.docker.desktop.address` ラベルで公開する(`internal/desktop`)
- PID ファイル
  - 実行中プロセスの PID(プロセス ID)だけを書いた小さなファイル。「すでに誰かが動いているか」を後から判定する古典的な手法
  - Compose は `<実行時ディレクトリ>/<プロジェクト名>.pid` を作り、`Lock()` で**自分自身の PID** を書く。書く前に既存ファイルを読み、そこにある PID のプロセスが生存していれば多重起動としてエラーにする
  - **ファイル名がプロジェクト名なので、別プロジェクトなら別ファイル = 同時起動できる**(意図的)。使っているのは `docker compose watch` のみで、`up`/`down` に排他制御は無い
  - 弱点は PID の再利用による誤検知。`flock` 等の OS ロックならプロセス終了時に自動解放されるためこの問題は起きないが、実装は単純さを優先している
- メモリ内ネットワーク(memnet)
  - `unix://` と `npipe://` という「TCP/IP を使わないホスト内接続」をまとめて扱う内部パッケージ名
  - `DialEndpoint` がエンドポイント文字列のスキームを見て、OS ごとの実装に振り分ける
- Windows 名前付きパイプ
  - Unix ドメインソケットに相当する Windows の同一ホスト内 IPC 機構。`\\.\pipe\<名前>` という名前で識別され、`npipe://` スキームで表される
  - 実装を持つのは `conn_windows.go` のみで、非 Windows では `conn_unix.go` がエラーを返す
- SHA256 ダイジェスト
  - データ全体を SHA-256 に通して得る 16 進 64 文字の値。同じ内容なら必ず同じ値、1 バイト違えば全く別の値になり、値から元データは復元できない
  - OCI ではこれを `sha256:abcd...` の形で blob の**名前そのもの**に使う(内容アドレス指定)。名前が中身から決まるので、改ざん検知・重複排除・pull 済み判定が名前の一致だけで成立する
- マニフェスト / blob
  - blob = レジストリに保存される中身そのもの(バイト列)。SHA256 ダイジェストで内容アドレス指定される
  - マニフェスト = 「どの blob が、どの mediaType・サイズで構成要素になっているか」を列挙する JSON。イメージやアーティファクトの目次にあたる
  - マニフェスト自身も blob として保存されダイジェストを持つ。タグは「マニフェストのダイジェストに付けた別名」で、参照は `タグ → マニフェスト → 各 blob` と連鎖する
- OCI アーティファクトの layer
  - OCI レジストリはコンテナイメージ以外の任意データ(= アーティファクト)も保存でき、その構成要素 1 つ 1 つが layer(= blob + mediaType)
  - **イメージのレイヤーと別概念ではなく、同じ仕組みの別の使い方**。イメージの layer は tar.gz のファイルシステム差分で重ね合わせて rootfs になるが、アーティファクトの layer は単なるデータの入れ物で重ね合わせの意味はない
  - `docker compose publish` は compose.yaml や .env をそれぞれ layer として格納し、それらを束ねたマニフェストを push する
- 最小限のパス集合(`EncompassingPaths`)
  - 与えられたパス群から、親に吸収されるものを取り除いて「全部を包含する最小の集合」に畳み込んだもの(`/a` と `/a/b` なら `/a` だけ残す)
  - watch は複数サービスの `develop.watch` からパスを集めるため親子が混ざる。再帰監視が使える環境では親を登録した時点で子もカバー済みなので、畳み込まないと**同じ変更でイベントが二重に飛び**、inotify の監視ハンドル(`max_user_watches` に上限あり)も無駄に消費する
  - そのため畳み込みは `isWatcherRecursive` が true のときだけ行う(`pkg/watch/watcher_naive.go:77`)
- 分散トレーシング
  - 1 つの処理をスパン(区間)の木として記録し、どこで時間がかかったか・どこで失敗したかを追えるようにする仕組み。OpenTelemetry(OTel)がその標準仕様
  - 「分散」は本来複数サービスを跨ぐ計測を指すが、Compose では CLI 1 プロセスの実行を計測する用途で使っている
- OTLP エクスポーター
  - OTLP = OpenTelemetry Protocol。集めたトレースを受信側へ送るための標準プロトコル(Compose は gRPC 版を使う)
  - エクスポーターは実際に送信を担う部品。送信先は `OTEL_` 環境変数か Docker コンテキストのメタデータから決まり、未設定なら何も送らない
