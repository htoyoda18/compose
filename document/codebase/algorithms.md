## 0. グラフという考え方

**グラフ**は、「もの（**ノード**、頂点）」と「もの同士の関係（**辺**、エッジ）」だけで世界を表す道具。

```
  web ──→ db
   │
   └────→ cache
```

- ノード: `web`, `db`, `cache`（Compose ではサービス）
- 辺: `web → db`、`web → cache`（「web は db に依存する」）

辺に向きがあるものを**有向グラフ**と呼ぶ。「A が B に依存する」は向きのある関係なので、Compose の依存関係は有向グラフになる。
さらに、辺をたどってぐるっと元に戻ってくる道（**循環**、サイクル）が無い有向グラフを **DAG**（Directed Acyclic Graph、有向非巡回グラフ）と呼ぶ。
**依存関係は DAG でなければならない**。輪になっていると「どれから始めればいいか」が決まらないからだ（→ 2 章）。

よく出てくる言葉:

| 言葉 | 意味 | Compose のコードでの名前 |
| ---- | ---- | ------------------------ |
| 子（child） | 自分が依存している相手（辺の先） | `Vertex.Children` |
| 親（parent） | 自分に依存している相手（辺の元） | `Vertex.Parents` |
| 葉（leaf） | 子がいない＝何にも依存していないノード | `Graph.Leaves()` |
| 根（root） | 親がいない＝誰からも依存されていないノード | `Graph.Roots()` |

上の例だと、`db` と `cache` が葉、`web` が根。

## 1. 依存グラフを作る

**解く問題**: compose.yaml の `depends_on` を、プログラムが扱える形（グラフ）にしたい。

**やり方**（2 段階）:

1. すべてのサービスをノードとして登録する
2. 各サービスの `depends_on` を見て、「サービス → 依存先」の辺を張る。張るときは、両側のノードに記録する
   - 依存する側の `Children` に依存先を入れる
   - 依存先の `Parents` に依存する側を入れる

両方向に記録しておくのは、あとで「子をたどる」（起動時）と「親をたどる」（停止時）の両方が必要になるから。

```yaml
services:
  web:   { depends_on: [db, cache] }
  db:    {}
  cache: {}
```

```
web.Children = {db, cache}     db.Parents    = {web}
                               cache.Parents = {web}
```

**細かい規則**:

- `depends_on` の相手が存在しないとき、`required: false`（任意の依存）なら辺を張らずに無視する。必須なら、エラーにする。
- 相手が profiles で無効になっているなら、「profile を有効にしてね」というエラーを出す。
- 最後に、循環が無いかを必ず確認する（→ 2 章）。

**コード**: `pkg/compose/dependencies.go` の `NewGraph`, `AddVertex`, `AddEdge`

## 2. 循環の検出（深さ優先探索）

**解く問題**: `a → b → c → a` のように依存が輪になっていたら、起動順が決められない。輪があるかを見つけて、エラーにしたい。

### 深さ優先探索（DFS）とは

迷路を「行けるところまで一本道で奥へ進み、行き止まりになったら一歩戻って別の道へ」という順で全部回る方法。
グラフでは「子をたどれるだけたどり、子が尽きたら戻る」になる。

### 輪の見つけ方

たどっている最中に、各ノードを 3 つの状態で管理する。

| 状態 | 意味 | コードの変数 |
| ---- | ---- | ------------ |
| 未訪問 | まだ来ていない | どちらにも入っていない |
| 探索中 | 今たどっている道の途中にいる（まだ奥を調べている） | `discovered` |
| 完了 | そこから先を全部調べ終わった | `finished` |

ポイントは 1 つだけ。**子をたどったら、その子が「探索中」だった**＝今いる道の途中に戻ってきた＝**輪がある**。

```
a → b → c → a
探索中: [a, b, c] のとき、c の子 a が「探索中」にいる → 輪
```

「完了」の子に当たるのは問題ない。別の道からもう調べ終わっている、という意味なので、もう一度たどる必要も無い（同じところを何度も調べない工夫）。

Compose はたどってきた道（`path`）も持ち歩いているので、エラーメッセージに輪そのものを出せる:

```
cycle found: a -> b -> c -> a
```

**コード**: `pkg/compose/dependencies.go` の `HasCycles`, `(*Graph).visit`

## 3. 依存順に処理する（トポロジカル順序）＋並列化

**解く問題**: 依存先から先に起動したい（db → web）。止めるときは逆に、依存する側から先に止めたい（web → db）。
しかも、関係の無いサービス同士は**同時に**処理して速くしたい。

### トポロジカル順序とは

DAG のノードを「どの辺についても、依存先が先に来る」ように 1 列に並べたもの。起動の正しい順番そのもの。
1 列に並べる代わりに、「**今すぐ処理してよいもの**を全部同時に処理し、終わったら次に処理してよくなったものを始める」とすれば並列化できる。Compose はこの方法を取っている。

### 起動（`InDependencyOrder`）の流れ

```
        web
       /   \
     db    cache        db と cache は葉（何にも依存しない）
```

1. 葉（`db`, `cache`）から始める。この 2 つは互いに関係無いので**同時に**処理する。
2. 1 つ終わるたびに、その親（`web`）を見に行く。
3. 親は、**子が全員「起動済み」になるまで待つ**。`db` だけ終わった時点では、`cache` が未起動なのでまだ始めない。
4. `cache` も終わったら `web` を始める。
5. 全ノードを処理したら終わり。

ポイント:

- 「子が全員終わったか」は、各ノードの状態（`ServiceStopped` / `ServiceStarted`）を見て判断する。
- `db` の完了と `cache` の完了は別々の goroutine から同時に届く。そのため、`web` を 2 回始めてしまわないよう「もう始めたか」の記録（`seen`）をロック付きで管理している（`consume`）。
- 終わったノードは channel（`nodeCh`）で 1 か所に知らされ、そこから親を見に行く。

### 停止（`InReverseDependencyOrder`）は向きを逆にするだけ

同じ仕組みで、「葉 ↔ 根」と「子 ↔ 親」を入れ替える。

| | 起動 | 停止 |
| --- | --- | --- |
| 始める場所 | 葉（`Leaves`） | 根（`Roots`） |
| 次に見に行く相手 | 親（`GetParents`） | 子（`GetChildren`） |
| 待つ条件 | 子が全員「起動済み」 | 親が全員「停止済み」 |

`upDirectionTraversal` と `downDirectionTraversal` は、この表の中身を差し替えた設定にすぎない。アルゴリズム本体（`visit` / `run`）は共通。

### 一部のサービスだけ処理する（`WithRootNodesAndDown`）

`docker compose down web` のようにサービスを指定したときは、「指定したサービス」と「それに依存しているサービス全部」（`getAncestors` で親をたどれるだけたどる）だけを処理する。
それ以外は `ignored` に入れて、順番の計算には参加させるが、実際の処理（`visitorFn`）は呼ばない。

**コード**: `pkg/compose/dependencies.go` の `InDependencyOrder`, `InReverseDependencyOrder`, `graphTraversal.visit` / `run` / `consume`, `WithRootNodesAndDown`

## 4. 依存を待ってから動く（plan engine の DAG 実行）

**解く問題**: 3 章と同じく「依存順に、並列に」実行したい。ただし plan engine では、ノードがサービスではなく「コンテナを作る」「ネットワークを作る」「名前を変える」のような**細かい操作**になる（[plan-engine.md](./plan-engine.md)）。

### 3 章とのやり方の違い

3 章は「終わったノードが、次に始められる相手を**探しに行く**」方式だった。
plan engine の executor は逆で、**全ノードを最初から同時に待機させ、各ノードが自分の依存先が終わるのを待つ**。

```
操作1: ネットワーク作成    操作2: db コンテナ作成（1 を待つ）    操作3: web コンテナ作成（1 と 2 を待つ）

全部を同時に起動
 ├─ 操作1: 待つものが無い → すぐ実行 → 終わったら「完了の合図」を出す
 ├─ 操作2: 操作1 の合図を待つ → 実行 → 合図を出す
 └─ 操作3: 操作1 と 操作2 の合図を待つ → 実行 → 合図を出す
```

「完了の合図」には、Go の **channel を close する**仕組みを使う（`rs.done[node.ID]`）。
close された channel は、何人が何回待っていても全員すぐに受け取れるので、「1 回の合図を大勢に知らせる」のにちょうどよい。

### 失敗したとき

- 依存先が失敗したら、自分は実行せずに「依存先が失敗した」として終わる（`failedDependency`）。その失敗は、さらに自分を待っているノードにも伝わる。
- どんな終わり方をしても必ず合図を出す（`defer close(...)`）。合図を出し忘れると、待っている側が永遠に止まってしまうから。

### 循環が無いことが前提

全員が「相手の合図」を待つ方式なので、もし輪があると全員が待ち合って永遠に止まる（デッドロック）。
plan は reconciler が依存先を先に作ってから依存する側を作る形で組み立てるので、輪はできない。

**コード**: `pkg/compose/executor.go` の `run`, `runPhase`, `runNode`、`pkg/compose/plan.go` の `PlanNode.DependsOn`

## 5. 同時に動かす数を制限する（セマフォ）

**解く問題**: 並列にすると速いが、100 個のコンテナを同時に作るとデーモンやネットワークが詰まる。`--parallel 4` のように、同時に動く数に上限を付けたい。

### セマフォとは

「入場券が N 枚しかない入り口」。処理を始める前に券を 1 枚取り（acquire）、終わったら返す（release）。
券が無ければ、誰かが返すまで待つ。これで同時に動くのは最大 N 個になる。

Compose では 2 つの形で使っている。

| 道具 | 何を数えるか | 使いどころ |
| ---- | ------------ | ---------- |
| `errgroup` の `SetLimit(N)`（`newLimitedErrgroup`） | goroutine 1 つまるごと | 「1 つの処理＝1 つの goroutine」で済む場合 |
| `semaphore.Weighted`（`newOptionalLimiter` + `acquireSlot` / `releaseSlot`） | 処理の一部分だけ | 「ログの流し始めだけ数える」など、goroutine 全体を数えると困る場合 |

### よくある落とし穴（レビューで何度も指摘されているもの）

**券は 1 か所で配らないと意味が無い**。たとえば `down` で、サービスごとに新しく N 枚の券を作ると、
サービスが 4 つ同時に動けば合計 4N 個が同時に動いてしまう。だから `down` や `restart` は、券の束を最初に 1 つだけ作って全サービスで共有している（`TestDown_ConcurrencyIsBoundedAcrossServices` がこれを確認している）。

なお `maxConcurrency` が 0 以下なら「無制限」の意味にする。`SetLimit(0)` は Go では「0 個しか動かせない」＝永遠に止まる、という意味になってしまうためだ（`newLimitedErrgroup` の中で 0 以下なら `SetLimit` を呼ばない）。

**コード**: `pkg/compose/compose.go` の `newLimitedErrgroup`, `newOptionalLimiter`, `acquireSlot`, `releaseSlot`

## 6. 差分を取る（望ましい状態と実際の状態の比較）

**解く問題**: compose.yaml に書かれた「こうあってほしい」と、Docker 上の「今こうなっている」を比べて、必要な操作だけを決めたい。
これが Compose の中心（**宣言的**な動き。[concepts/intro.md](../concepts/intro.md#命令的-imperative-から宣言的-declarative-へ)）。

### 考え方は「2 つの集合の比較」

望ましいもの（D）と、実際にあるもの（O）を、同じ名前（キー）で突き合わせる。

| 状況 | 判断 |
| ---- | ---- |
| D にあって O に無い | 作る |
| 両方にあって、中身が同じ | 何もしない |
| 両方にあって、中身が違う | 作り直す |
| O にあって D に無い | 孤児（orphan）。`--remove-orphans` なら消す。ネットワークやボリュームは、データを失わないよう基本は残して警告する |

「中身が同じか」を毎回全項目比べるのは大変なので、ハッシュで比べる（→ 7 章）。

### Compose ならではの工夫

- **突き合わせのキーはラベル**。Compose は自分の状態を保存しないので、Docker 上のリソースに付けたラベル（`com.docker.compose.project` / `service` など）で、「これは compose.yaml のどれか」を判定する。
- **同じキーのものが複数あったとき**（名前を変えたあとの残骸など）は、一番合うものを 1 つ選び、残りは孤児として警告だけ出す（`resolveObserved`）。毎回同じものが選ばれるよう、選び方を固定している。
- **ハッシュが記録されていないもの**（古い Compose や手で作ったネットワーク）は、作り直さずにそのままにする。違いが「設定の変更」なのか「わざと手で作った」のか区別できないからだ。

比べた結果は、操作の DAG（Plan）として出力され、4 章の executor が実行する。

**コード**: `pkg/compose/reconcile.go` の `reconcile`, `resolveObserved`, `reconcileNetworks` など、`pkg/compose/observed_state.go` の `collectObservedState`

## 7. ハッシュで「変わったか」を判定する（config-hash）

**解く問題**: サービスの設定（イメージ・環境変数・ポート・ボリューム…）が前回から変わったかを、素早く確実に判定したい。

### ハッシュとは

どんな大きさのデータでも、決まった長さの「指紋」のような値に変換する計算。Compose は SHA-256 を使う。性質は 2 つ。

- 同じデータからは、必ず同じ値が出る
- データが 1 文字でも違えば、まったく違う値になる（偶然一致することは実質無い）

だから、作成時の設定のハッシュをコンテナのラベル（`com.docker.compose.config-hash`）に保存しておく。
次の `up` では、今の設定のハッシュと比べるだけで「変わったか」がわかる（6 章の「中身が同じか」）。

### 落とし穴: 「同じ設定」を必ず同じバイト列にする

ハッシュはバイト列に対して計算するので、**意味が同じでも並び順が違うと別の値になる**。

- 設定を JSON にしてからハッシュを取る。このとき、JSON のキーの並び順を、固定のリスト（`serviceHashKeyOrder`）で決め打ちしている（`pinRootKeyOrder`）。
  - そうしないと、依存ライブラリ（compose-go）がコード上で項目の順番を入れ替えただけで、全ユーザーのハッシュが変わってしまう。そうなると、Compose を更新した直後の `up` で全コンテナが作り直される。
- 作り直しに関係しない項目（ビルドの設定、レプリカ数、`depends_on` など）は、ハッシュを取る前に取り除く（`trimServiceHashFields`）。たとえばレプリカ数を変えただけで、既存のコンテナを作り直す必要は無いからだ。

**コード**: `pkg/compose/hash.go` の `ServiceHash`, `trimServiceHashFields`, `serviceHashKeyOrder`

## 8. まとめて処理する（デバウンス）

**解く問題**: `watch` 中にエディタで保存したり `git checkout` したりすると、ファイル変更の通知が一瞬で何十・何百と届く。
1 つ届くたびに同期や再ビルドをしていたら大変なことになる。**落ち着くまで待ってから、まとめて 1 回**処理したい。

### デバウンスとは

「最後の変更から一定時間（静かな時間）何も起きなかったら、それまでの分をまとめて処理する」方法。エレベーターの扉が「最後の人が乗ってから少し待って閉まる」のと同じ。

```
変更 変更 変更 ────(静かな時間)────→ まとめて 1 回処理
                 ↑ 途中で変更が来たら、待ち時間をやり直す
```

Compose の実装（`BatchDebounceEvents`）:

1. 届いた変更を、重複を除いて貯めておく（同じファイルの変更が何回来ても 1 つ。集合 `seen` を使う）
2. 変更が届くたびにタイマーを最初からやり直す（`t.Reset(QuietPeriod)`。静かな時間 `QuietPeriod` は 500ms）
3. タイマーが鳴った＝静かな時間が続いた → 貯めた分を 1 つのまとまり（バッチ）として送り出す
4. 入力が閉じたら、残りを送り出して終わる

**コード**: `pkg/watch/debounce.go` の `BatchDebounceEvents`。受け取ったバッチの振り分けは `pkg/compose/watch.go` の `handleWatchBatch`

## 9. 連番を振る（レプリカのコンテナ番号）

**解く問題**: `scale` でコンテナを増やすとき、新しいコンテナに番号（`web-1`, `web-2`, … の数字）を振りたい。

**やり方**は単純で、**今ある番号の最大値 + 1**。

```
既存: web-1, web-3   →  最大は 3  →  新しい番号は 4
```

空いている番号（上の例の 2）を埋めないのは、わざと。番号はコンテナ名やラベル（`container-number`）に使われるので、
過去に使った番号を別のコンテナで使い回すと、ログやツールの上で取り違えが起きうる。最大値 + 1 なら、生きている間は必ず新しい番号になる。

ラベルが無い・数字でないコンテナは、警告を出して数えない。

**コード**: `pkg/compose/service_containers.go` の `nextContainerNumber`（reconcile の中から呼ばれる）

## 読んだあとに

- いちばん大事なのは 3 章と 4 章。`start` / `down` / `run` の依存処理は 3 章の仕組み、`up` / `create` は 4 章の仕組みで動いている。今は 3 章から 4 章へ移行している最中（エピック [#14081](https://github.com/docker/compose/issues/14081)）。
- 単体テストを読むと、動きが具体的にわかる。`pkg/compose/dependencies_test.go`（3 章）、`pkg/compose/executor_test.go`（4 章）、`pkg/compose/reconcile_test.go`（6 章）、`pkg/watch/debounce_test.go`（8 章）。
