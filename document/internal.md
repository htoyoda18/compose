- インメモリソケットについて
  - TCP のようにネットワークを介さず、同一ホスト上のプロセス間だけで通信する経路（Unix ドメインソケット `AF_UNIX`、Windows の名前付きパイプ `npipe`）
  - `internal/memnet` の `DialEndpoint` が `unix://`/`npipe://` 形式のエンドポイント文字列からこの経路への接続を確立する
  - `internal/desktop` が Docker Desktop との通信にこの仕組みを使っており、TCP よりオーバーヘッドが小さく外部に露出しない利点がある
- PID ファイルについて
  - 実行中プロセスの PID を書き込んでおくファイルで、同じプロセス（や排他したい処理）の多重起動を検出するために使われる
  - `internal/pidfile` の `Read`/`Write` が読み書きを担い、`Write` は既存ファイルが生存中の PID を指す場合にエラーを返して二重起動を防ぐ
  - `internal/locker` が compose プロジェクトごとの PID ファイルを実行時ディレクトリ配下に作成し、同一プロジェクトへの同時操作をロックする
- 実行時ディレクトリについて
  - プロセス実行中の一時データ（ソケットや PID ファイルなど）を置くための、OS が用意するディレクトリ
  - Linux では環境変数 `XDG_RUNTIME_DIR` が優先的に使われ、未設定の場合は OS ごとの既定パス（`internal/locker` の `runtime_*.go`）にフォールバックする
  - compose ではこの配下にロック用の PID ファイルを配置し、プロセス終了時にクリーンアップされることを前提にしている
- docker のレジストリについて
  - コンテナイメージを保存・配布するサーバーで、`docker.io`（Docker Hub）が既定のレジストリとして使われる
  - `internal/registry` がデフォルトのレジストリホスト（`registry-1.docker.io`）や認証用のインデックスサーバー（`index.docker.io`）の定数を定義する
  - `GetAuthConfigKey` がイメージ参照からレジストリ名を認証情報のキーに正規化し、Docker Hub 由来の名前表記ゆれ（`docker.io` 等）を吸収する
- マニフェスト/blob について
  - マニフェストはイメージやアーティファクトを構成する layer（blob）の一覧とメタデータを記述する JSON ドキュメント、blob は実際のバイナリデータ（レイヤーの中身）を指す
  - `internal/oci` の `resolver.go` がマニフェストの解決・取得（`Get`）と、マニフェストに含まれない blob 単体の取得（`GetBlob`）を別の API として提供する
  - `push.go` は compose.yaml や .env ファイルを blob として記述し、それらをまとめたマニフェストを生成してレジストリへ push する（`docker compose publish` 等）
- シンボリックリンクについて
  - あるパスから別のパスを指す「参照」で、実体を複製せずに別名やパスの付け替えを行える仕組み
  - `internal/paths` の `IsChild` はパス同士の親子関係を判定する際、大文字小文字の違いだけでなくシンボリックリンク越しでも同一ファイルを指しうることを考慮し、`os.SameFile` で実体を突き合わせて判定する
  - このような考慮がないと、watch の監視対象パスの集約などでシンボリックリンク経由のパスを誤って別ファイルとして扱ってしまう
