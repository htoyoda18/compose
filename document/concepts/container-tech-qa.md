# container-tech.md を読んで出た疑問 Q&A

[container-tech.md](./container-tech.md) を読んでいて出た疑問への短い回答。

← [document 一覧](../README.md)

## 1. マウントはどういう仕組みか（ファイルの同期なのか）

- マウントは**コピーや同期ではなく「つなぎ替え」**。カーネルが「このディレクトリ以下へのアクセスは、あのファイルシステム（ディスク・別のディレクトリなど）に転送する」という対応表を持っていて、読み書きのたびにそこへ振り分ける。
- bind mount（`-v ./src:/app`）なら、コンテナの `/app` とホストの `./src` は**同じ実体**を見ている。片方で書けば、もう片方からも即座に見える。同期が走るわけではない。
- ただし Mac / Windows では、ホストとコンテナの間に Linux VM があるので、VM 境界を越えるファイル共有（virtiofs など）が間に入る。これが「同期っぽく見える」理由で、遅くなる原因でもある（→ [intro.md](./intro.md#docker-は-linux-上でしか動かない)）。

## 2. mnt / uts / ipc とは

- **mnt**（mount namespace）: マウントの対応表をプロセスごとに分ける。だからコンテナ内でマウントしてもホストには見えず、コンテナはイメージの中身を自分の `/` として見られる。
- **uts**（UNIX Time-Sharing namespace）: ホスト名（とドメイン名）を分ける。コンテナごとに `hostname` が違うのはこれのおかげ。名前は昔の UNIX の構造体名に由来するだけで、意味は「ホスト名の分離」。
- **ipc**（Inter-Process Communication namespace）: 共有メモリやメッセージキューなど、プロセス間通信の仕組みを分ける。別のコンテナのプロセスとは、これらで勝手に通信できなくなる。

## 3. cgroup の上限を超えるとどうなるか

- **メモリ**: 上限を超えると、カーネルの OOM killer がコンテナ内のプロセスを強制終了する。Docker ではコンテナが exit code 137 で落ち、`docker inspect` で `OOMKilled: true` になる。
- **CPU**: 落ちはしない。上限の分しか CPU 時間が割り当てられず、**遅くなる**（スロットリング）だけ。
- **プロセス数**（`pids` の上限）: 新しいプロセスやスレッドを作ろうとした時点で失敗する（fork が `Resource temporarily unavailable` になる）。

## 4. ファイルシステムとは

- ディスクは本来「番号の付いたブロックの並び」でしかない。そこに**「ファイル名・フォルダ構造・中身の場所・権限」を記録して、ファイルとして読み書きできるようにする仕組み**がファイルシステム（ext4、APFS、NTFS など）。
- Linux ではさらに、すべてを 1 本の木（`/` から始まるディレクトリ構造）に見せる。ディスクのファイルシステムも、メモリ上の tmpfs も、`/proc` のようにカーネルの情報を見せるものも、マウントでこの木のどこかにつないで使う。
- overlayfs もその一種で、実体を持たずに「下の複数の層を重ねて 1 つに見せる」ファイルシステム。

## 5. virtiofs はどうやって VM 境界を越えてファイルを共有しているのか

- VM の中の Linux からは、ホストの共有フォルダが**普通のファイルシステムとしてマウントされているように見える**。実際には、VM 内で `open` や `read` が呼ばれると、その要求がメッセージとして VM の外のホスト側プロセス（Docker Desktop なら仮想化の仕組みの中のデーモン）に送られ、ホストがホストのディスクを読んで結果を返している。
- 要求のやり取りには FUSE（ユーザー空間でファイルシステムを実装する仕組み）の形式を使い、VM とホストの通信には virtio（仮想マシン用の高速な仮想デバイスの規格）の共有メモリを使う。だからネットワーク越しの共有（NFS や SMB）より速い。
- それでも、ファイル 1 回の操作ごとに VM の境界を行き来するので、ネイティブより遅い。特に `node_modules` のように小さなファイルが大量にあると差が大きい。また、変更の通知（inotify）はこの経路を素直には通らないので、`watch` が取りこぼす原因にもなる。

## 6. ホスト名とは（特定のコンピュータを指すものか）

- おおむねその理解で合っている。ホスト名は、**OS が自分自身に付けている名前**（`hostname` コマンドで見られる）。ネットワーク上で「このマシン」を人間にわかる名前で呼ぶためのもの。
- ただし、それだけで世界中から一意に特定できるわけではない。他のマシンから名前で届くには、DNS や `/etc/hosts` で「名前 → IP アドレス」の対応が登録されている必要がある。ホスト名は「自分の名乗り」、DNS 名は「みんなが引ける住所録の名前」と分けて考えるとわかりやすい。
- コンテナの場合、uts namespace のおかげで、1 台のマシンの中でもコンテナごとに別のホスト名を名乗れる（デフォルトはコンテナ ID の先頭）。Compose では、サービス名で通信できるのはホスト名ではなく、Docker の内蔵 DNS がサービス名を引けるようにしているから（→ [networking.md](./networking.md)）。
