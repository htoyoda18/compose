2026-10 の 3 回の調査と、11-05 の定点観測から引き出した。PR の出し方やメンテナとのやり取りの注意は [pr-trends.md の §8](../contributing/pr-trends.md#8-contributing--ai_policy-のルール外部コントリビューター向けの要点) にある。

## クリティカルさの物差し

影響（重さ × 人数）で測る。重さは「気付かれにくさ」で上がる。終了コード 0 のまま間違える、データが黙って消える、黙って止まる、など（N1、N2、N7、#14244）。
だから、どの調査でも、終了コードではなく**最後の状態**（データ、コンテナの状態、残ったリソース）を確かめる。

### 優先順位の付け方

影響（重さ × 影響を受ける人の数）と、難易度（規模、合意の要否、衝突、原因が分かっているか）を天秤にかける。影響が大きく難易度が低いものが先。次のリリースに入る退行は 1 段上げる。

- データ消失 > セキュリティ > 未リリースの退行 > 固まる・落ちる > 誤った挙動 > 性能 > 使い勝手、という種類の順は、重さを見積もる材料の 1 つにとどめる。
- 小さく直せる重いものが、最も受け入れられやすい（#14358、#14363）。

## どの方向から何が見つかったか

## 方針 1: 決まった間隔で回す「定点観測」

時間がたてば、新しい変更で新しい問題が入る。特に plan engine（#14081 の Lot 2 / Lot 3）と、サービス選択（#14346）は大きく変わり続けているので、退行が入りやすい。

| 間隔 | やること | 狙い |
| ---- | -------- | ---- |
| 毎週（軽く） | 新しくマージされた PR の差分を、下の「バグの型」で読む。新しい issue のうち、再現できる bug を拾う | 入った直後の問題を、最初に見つける |
| リリースの前（main に未リリースのコミットが溜まったとき） | リリース版と main を、同じシナリオで比べる。API 呼び出しの数も比べる | 退行を、リリースされる前に止める（N1 の型） |
| 月に 1 回（深く） | 下の「攻撃面」か「バグの型」を 1 つ選んで、深掘りする | 重大なものを見つける |

正常系を 1 回ずつ流すだけでは足りない。重大な問題は、異常系、2 回目以降の実行、繰り返し、組み合わせに隠れる。#14426（`up` が固まる）は、報告者が 12 回繰り返して、半分で固まるのを見つけた。

## 方針 2: 「バグの型」で兄弟を探す

1 つ見つけたら、同じ形をコード全体から grep で探す。`run` の `Inherit` の渡し漏れ（#14358）を見つけた後、同じ形を探すと `scale` にもあった（N10）。今までに当たった型:

- **設定の渡し漏れ**: Options のフィールドを書き忘れると、Go の既定値（false、nil）になり、それが危ない側になる（`Inherit`、`Timeout`）。
- **パスの照合の食い違い**: フルパスで照合する場所と、ファイル名で照合する場所が混ざっている（`.git`、`.dockerignore`）。
- **名前だけで持ち主を判断する**: ラベルを見ずに、名前だけで他人のリソースに触る（N2）。
- **doc コメントと実装の食い違い**: コメントに書かれた約束を、実装が守っていない（S1、#14310）。
- **docker CLI との差**: compose が作り直した機能に、CLI にある保護や挙動が無い（S1、N4）。
- **シグナルとキャンセルの扱い**: ctx が伝わらない、同じシグナルを 2 か所で受ける、1 つの失敗が無関係な処理まで止める（N1、N3 の関連）。
- **`up` ではやっているのに `run` ではやっていない**: よく使うコマンドどうしの食い違い。新しい issue が少ない時期は、issue よりコードを読むほうが候補が見つかる。

## 方針 3: 「攻撃面」を、信頼されない側から見る

Docker の立場では「compose.yaml は信頼されるもの」なので、それ以外の立場から権限の境界を越えられるかを見る。

- **乗っ取られたコンテナの中のプロセス**: `compose cp`（コンテナからホストへ）、`logs` や `attach` の出力、watch の同期先
- **外から取ってきた compose の配布物**（OCI、git の remote include）: 取得、展開、変数の展開、確認の表示
- **同じコンテナの中の、権限の低いプロセス**: compose が注入するもの（secrets、configs など）
- **同じホストの別のプロジェクト**: ラベルや名前で他人のリソースに触る処理

試すときの注意:

- 普段使いの Docker ではなく、使い捨ての VM で試す。認証情報は偽物だけにする。
- セキュリティに関わるものは、security@docker.com に非公開で報告する。**メモはこの公開リポジトリの外に置き、詳細をここに書かない**（S1）。

## 方針 4: 境界とバージョンの変化を追う

- buildx、Docker Engine の API、compose-go が新しくなると、compose との組み合わせで問題が出やすい（#14363、N5）。
- dependabot の compose-go の更新 PR や、Docker Desktop の新しいリリースが出たら、bake への変換や watch の動きを確かめる。

## 調べるときの注意

- **違いを見つけたら、どちらが設計上正しいかまで考える**。N1 は「v5.6.0 との違い」から退行と判断したが、ndeloof の判断は「フェーズ全体を止めるのは意図どおりで、問題は報告の仕方」だった。v5.6.0 の挙動もタイミング任せだった。
- **2 つの調査が別々の方法で同じものを見つけたら、確度が高い**（N6）。
- **結果がすべて同じになったら、まず自分のスクリプトを疑う**。11-05 は、macOS に `timeout` が無く、最初の実行が全部 `rc=127` だった（perl の `alarm` で代用した）。
- **性能は、時間ではなく API 呼び出しの数で測る**。同じ Docker を他の作業と共有していると、時間は大きくぶれる。呼び出しの数は、何度測っても同じだった。
- **並行の調査で設定を共有しない**。一時的な Docker の設定（`DOCKER_CONFIG`）を共有すると、ある調査が builder の選択を変えたときに、他の調査の結果が変わりうる。
- **揺さぶりは、1 つのプロジェクトの中に詰め込む**。別々のプロジェクトを並列に回しても、プロジェクトの中の競合（#14426 の型）は出にくかった（T3、480 回で 0 件）。依存の鎖、healthcheck、途中の終了を 1 つのプロジェクトに入れる（T3b）。
- **`config --hash` は、実際の作り直しの判定と同じではない**。T1 では `use_api_socket` の差が出なかったが、実機の T2 では作り直された。アップグレードの確認は実機で。
- **watch の調査では、ログを監視の外に書く**。監視対象のディレクトリの中に書くと、それ自体が再ビルドを起こす（#14363 で 1 度誤った）。
