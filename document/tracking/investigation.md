← [document 一覧](../README.md)

[next-tasks.md](./next-tasks.md) の候補を見つけるときに使う、長く使える方針と注意。
2026-10 の 3 回の調査、11-05 の定点観測、メンテナが 2026-09〜11 にマージした PR（dependabot を除く 138 本）の分析から引き出した。
PR の出し方やメンテナとのやり取りの注意は [pr-trends.md の §8](../contributing/pr-trends.md#8-contributing--ai_policy-のルール外部コントリビューター向けの要点) にある。

## クリティカルさの物差し

影響（重さ × 人数）で測る。重さは「気付かれにくさ」で上がる。終了コード 0 のまま間違える、データが黙って消える、黙って止まる、など（N1、N2、N7、#14244）。
だから、どの調査でも、終了コードではなく**最後の状態**（データ、コンテナの状態、残ったリソース）と、**出力そのもの**を確かめる。

### 優先順位の付け方

影響（重さ × 影響を受ける人の数）と、難易度（規模、合意の要否、衝突、原因が分かっているか）を天秤にかける。影響が大きく難易度が低いものが先。次のリリースに入る退行は 1 段上げる。

- データ消失 > セキュリティ > 未リリースの退行 > 固まる・落ちる > 誤った挙動 > 性能 > 使い勝手、という種類の順は、重さを見積もる材料の 1 つにとどめる。
- 小さく直せる重いものが、最も受け入れられやすい（#14358、#14363）。

## 外から勝てる場所

- **issue の一覧からは勝てない**。fix に紐づく issue は、ほぼすべて利用者の報告で、ndeloof が数日で直している（#14386 → #14393、#14426 → #14427 など）。
- **利用者が報告しているのは、リリース後の退行が多い**（#14386「v5.5.1 から」、#14287、#13985、#14285、#14465）。だから、外から勝てるのは**利用者が気付く前に見つける**ところ。
- 退行は、**機能の幅に散らばっている**（`use_api_socket`、pre_start の env、profiles と build、OCI と `--project-directory`、`run` の pull の進捗）。シナリオの数を増やすより、機能ごとに確かめるほうが当たる（[方針 5](#方針-5-地図を作って穴から見る)）。
- **仮説**: メンテナが普段使わない環境（ssh の Docker、rootless、古い API、classic builder）には、見落としが残りやすい。根拠は N5、N12、N13 の 3 件だけなので、T17 で確かめる（[方針 6](#方針-6-使われ方と環境を変える)）。

### 狙う場所（当たりやすい順。2026-11-06 時点）

| 方向 | なぜ当たりやすいか | 手がかり |
| ---- | ------------------ | -------- |
| 1. 不安定なテスト | 競合は負荷の高い CI でしか出ない。メンテナはここから本物のバグを見つけている | 毎週の CI の失敗（T9）。#14140、#14314 |
| 2. plan engine の書き換えの跡 | 古いコードから責務を移すたびに、抜け（N8、#14393）か二重（#14467）が出ている | 新旧の経路の副作用（イベント、フック、ラベル、警告）を 1 つずつ比べる（T4） |
| 3. 機能の幅と出力 | 利用者の報告した退行は、機能の幅に散らばっていた。版の差に出ない古いバグは、出力を読めば見える | 機能の表（T4、T5〜）、出力の異常（T11） |
| 4. 時間の窓と中断 | 2 つの呼び出しの間や、途中で kill されたときの状態は、1 回の実行では出ない | T12、T13、T3c、T3d |
| 5. アップグレード | ほぼ全員が通る。設定ハッシュやラベルの扱いが変わると、変更していないコンテナまで作り直される | #14402、#14405。T1 と T2 は済み |
| 6. 信頼できない入力 | 境界を越えると影響が大きい | S1。見つけたら非公開で報告する |

## 方針 1: 決まった間隔で回す「定点観測」

時間がたてば、新しい変更で新しい問題が入る。特に plan engine（#14081）、`internal/` への移動（#14397〜#14410）、サービス選択（#14346）は大きく変わり続けているので、退行が入りやすい。

| 間隔 | やること | 狙い |
| ---- | -------- | ---- |
| 毎週（軽く） | main の CI の失敗を集め、flake ごとに「製品の競合か」を疑う（T9）。新しくマージされた PR の差分を、下の「バグの型」で読む | 入った直後の問題を、最初に見つける |
| リリースの前（main に未リリースのコミットが溜まったとき） | リリース版と main を、機能の表に沿って比べる。終了コードと状態だけでなく、`--progress json` の出力も比べる | 退行を、リリースされる前に止める（N1 の型） |
| 月に 1 回（深く） | 下の「バグの型」か「攻撃面」を 1 つ選んで、深掘りする | 重大なものを見つける |

正常系を 1 回ずつ流すだけでは足りない。重大な問題は、異常系、2 回目以降の実行、繰り返し、組み合わせに隠れる。#14426（`up` が固まる）は、報告者が 12 回繰り返して、半分で固まるのを見つけた。

## 方針 2: 「バグの型」で兄弟を探す

1 つ見つけたら、同じ形をコード全体から grep で探す。`run` の `Inherit` の渡し漏れ（#14358）を見つけた後、同じ形を探すと `scale` にもあった（N10）。

| 型 | 例 | 探し方の手がかり |
| -- | -- | ---------------- |
| **設定の渡し漏れ** | `Inherit`（#14358、N10）、`Timeout`（N4） | Options の構造体リテラルを grep し、他の呼び出し元と比べる。Go の既定値（false、nil、0）が危ない側になっていないか（`SetLimit(0)` が「無制限」でなく「0 個」になった #14177） |
| **パスの照合の食い違い** | `.git`、`.dockerignore`（N6）、`..local`（#14425） | フルパスで照合する場所と、ファイル名で照合する場所が混ざっていないか。`strings.HasPrefix(rel, "..")` のような自作の判定（`filepath.IsLocal` があるのに） |
| **名前だけで持ち主を判断する** | N2 | ラベルを見ずに、名前で他人のリソースに触る処理 |
| **doc コメントと実装の食い違い** | S1、#14310、#14353 | doc コメントに書かれた約束（「止めない」「出力を流す」）を 1 つずつ確かめる |
| **docker CLI との差** | S1、N4、#14402 | compose が作り直した機能を、同じ名前の docker CLI の機能と比べる |
| **シグナルとキャンセルの扱い** | N1、#14309、#14227 | ctx が伝わらない、同じシグナルを 2 か所で受ける、キャンセルを別の失敗として報告する |
| **時間の窓** | #14304（一覧 → 購読）、#14335（パイプ → `Wait`） | 2 つの呼び出しの間に状態が変わったら壊れる箇所。`ContainerList` の後の `Events`、`inspect` の後の操作、`cmd.Wait()` と出力の読み取りの順 |
| **中断の後の途中状態** | #14462（展開の途中で kill）、T3d（作成中の Ctrl-C） | 「ディレクトリがあれば完成」のように、存在だけで完了と見なす判定。一時ファイルに書いて最後に rename していない処理 |
| **責務を移したときの抜けと二重** | 抜け: N8、#14393。二重: #14467（イベントが 2 回） | 移した先と元の両方で、イベントや警告を出していないか。元にあった副作用が、移した先にもあるか |
| **ルールの隙間** | #14264（provider に変えたサービスの古いコンテナを、誰も消さない） | 「このルールは X を除く」が重なったときに、どのルールの担当でもない状態ができないか |
| **順序が決まらない** | #14213（`sort.Slice`）、`images --format json` の順序 | `sort.Slice` で同じ値の順、map の走査の順を、そのまま出力や「最初の 1 つ」に使っている箇所 |
| **普通でない入力** | #14380（ドットを含むサービス名）、IPv6 | 名前のドット・ハイフン・大文字・非 ASCII、空のリスト、`..` で始まる名前、IPv6 だけの環境 |
| **`up` ではやっているのに `run` ではやっていない** | #14358 | よく使うコマンドどうしの食い違い。issue が少ない時期は、issue よりコードを読むほうが見つかる |

### 見つけた後: 全部を調べて、仕組みで防ぐ形で出す

メンテナは 1 件の修正で終わらせず、同じ形を全部数えて、仕組みで防いでいる。

- #14150: `commit --dry-run` が本物のイメージを作る 1 件から、変更系の操作 39 個を全部確かめ、「分類していない API が増えたら失敗する」AST のテストを足した。
- #14177: `SetLimit(0)` の 1 件から、並列処理の全箇所を 1 つの helper に揃えた。

外から出すときも、「1 件の修正」より「同じ形が N 箇所ある。テストで防ぐ案がある」として issue に出すほうが、価値が伝わりやすい。
ただし、変更は 1 つの PR に収まる大きさにし、細かく分けすぎない（contribution farming）。どこまで広げるかは issue でメンテナに聞く。

## 方針 3: 「攻撃面」を、信頼されない側から見る

Docker の立場では「compose.yaml は信頼されるもの」なので、それ以外の立場から権限の境界を越えられるかを見る。

- **乗っ取られたコンテナの中のプロセス**: `compose cp`（コンテナからホストへ）、`logs` や `attach` の出力、watch の同期先
- **外から取ってきた compose の配布物**（OCI、git の remote include）: 取得、展開、変数の展開、確認の表示
- **同じコンテナの中の、権限の低いプロセス**: compose が注入するもの（secrets、configs、`use_api_socket` の認証情報など）
- **同じホストの別のプロジェクト**: ラベルや名前で他人のリソースに触る処理

試すときの注意:

- 普段使いの Docker ではなく、使い捨ての VM で試す。認証情報は偽物だけにする。
- セキュリティに関わるものは、security@docker.com に非公開で報告する。**メモはこの公開リポジトリの外に置き、詳細をここに書かない**（S1）。

## 方針 4: 境界とバージョンの変化を追う

- buildx、Docker Engine の API、compose-go が新しくなると、compose との組み合わせで問題が出やすい（#14363、N5、#14285「buildx >= 0.37.2 から」）。
- dependabot の compose-go や buildx の更新 PR、Docker Desktop の新しいリリースが出たら、bake への変換や watch の動きを確かめる。

## 方針 5: 地図を作って穴から見る

当てずっぽうに読むのではなく、「まだ誰も確かめていない場所」の地図を先に作り、穴から見る。

- **coverage の地図（T10）**: CI は run ごとに、unit と e2e のカバレッジを成果物（`coverage-data-unit`、`coverage-data-e2e-*`）として残している（`ci.yml` の coverage ジョブ）。`gh run download` で取り、`go tool covdata` で関数ごとにすると、0% の関数が分かる。0% の経路は、退行がそのまま通る（`runPostStartHooksOnEvent` は 0% だった）。
- **機能の表（T4）**: compose-spec の属性とトップレベル要素 × コマンド（`up`、`create`、`start`、`run`、`scale`、watch、`down`）の表。どの経路でどの属性を扱うか、コードの場所を書く。1 回に 1 機能ずつ確かめる（T5〜）。
- **出力の異常（T11）**: 版を比べても、古いバグは差に出ない（#14465 のイベントの二重は v5.4.0 からあった）。`--progress json` と `plain` の出力そのものを読み、同じ対象の行が 2 回、内部の名前（`service:web:1`）、終わりの表示の無い行（`Waiting` のまま）を探す。
- **静的解析を手がかりに使う（T16）**: `.golangci.yml` で有効になっていない analyzer（`nilerr`、`contextcheck`、`bodyclose`、`noctx`、`errchkjson`、`exhaustive`、`gosec` など）や `govulncheck` を手元で回し、本物のバグに見えるものだけを拾う。メンテナも linter を足したり上げたりするたびに指摘を直している（#14207、#14418）。**lint の指摘を直すだけの PR は出さない**（見た目だけの変更として閉じられる）。

## 方針 6: 使われ方と環境を変える

- **新しい使われ方**: コーディングエージェントが一度に多くのファイルを書き換える（#14202）、CLI と IDE が同時に同じプロジェクトを操作する（#14462）、CI の TTY の無い環境、`--progress json` を読むツール。
- **設定の移行**: 動いているプロジェクトの設定を 1 つ変えて、もう一度 `up` する（サービスの改名、profiles の付け外し、volume を external に、`network_mode` の変更、provider への移行（#14264）、replicas の増減）。古いリソースが残らないか、失敗しないか。
- **メンテナが普段使わない環境（仮説）**: ssh の Docker（N13）、rootless、古い API（`DOCKER_API_VERSION`。N12 は API 1.52 未満で挙動が変わる）、classic builder（10）、Windows のパス。

## 調べるときの注意

- **違いを見つけたら、どちらが設計上正しいかまで考える**。N1 は「v5.6.0 との違い」から退行と判断したが、ndeloof の判断は「フェーズ全体を止めるのは意図どおりで、問題は報告の仕方」だった。v5.6.0 の挙動もタイミング任せだった。
- **版を比べて差が無くても、正しいとは限らない**。差に出ない古いバグは、出力や状態そのものを読んで見つける（#14465）。
- **不安定なテストを再試行で片付けない**。まず製品の競合を疑う。負荷の高い CI でしか開かない時間の窓がある（#14314: 再起動の間隔 100 ms に対し、ストリームを開くまで数百 ms かかる）。
- **2 つの調査が別々の方法で同じものを見つけたら、確度が高い**（N6）。
- **結果がすべて同じになったら、まず自分のスクリプトを疑う**。11-05 は、macOS に `timeout` が無く、最初の実行が全部 `rc=127` だった（perl の `alarm` で代用した）。11-07 の T10b でも、ドットを含むプロジェクト名、余計な `$PWD/`、bash 3.2 の空の配列と `set -u` で、版の比べ方が 3 回崩れた。直した後も同じなら、版を通じて同じ形のコードかを読んで確かめる（N19 は 5.0.1 も同じ形だった）。
- **シグナルの調査は、シェルの背景ジョブを通さずに確かめる**。シェルの都合（背景ジョブと SIGINT の扱い、標準入力）が結果に混ざる。Python の `subprocess` から送る（`double-sigint.py`）と、比べる対照になる。
- **性能は、時間ではなく API 呼び出しの数で測る**。同じ Docker を他の作業と共有していると、時間は大きくぶれる。呼び出しの数は、何度測っても同じだった。
- **並行の調査で設定を共有しない**。一時的な Docker の設定（`DOCKER_CONFIG`）を共有すると、ある調査が builder の選択を変えたときに、他の調査の結果が変わりうる。
- **揺さぶりは、1 つのプロジェクトの中に詰め込む**。別々のプロジェクトを並列に回しても、プロジェクトの中の競合（#14426 の型）は出にくかった（T3、480 回で 0 件）。依存の鎖、healthcheck、途中の終了を 1 つのプロジェクトに入れる（T3b）。
- **`config --hash` は、実際の作り直しの判定と同じではない**。T1 では `use_api_socket` の差が出なかったが、実機の T2 では作り直された。アップグレードの確認は実機で。
- **watch の調査では、ログを監視の外に書く**。監視対象のディレクトリの中に書くと、それ自体が再ビルドを起こす（#14363 で 1 度誤った）。
- **CI のログでは、`--- FAIL:` だけを探さない**。e2e は gotestsum の github-actions 形式で、色付きの `FAIL pkg/e2e.TestX (1.2s)` と出る。11-07 の T9 では最初これを取りこぼし、本物の flake を「exit code 2」としか分類できなかった。
- **CI の失敗は、`--status failure` の一覧だけを見ない**。再実行で green になった run の失敗は、その一覧に出ない。flake はまさにそこにいるので、再実行された run（attempt > 1）の最初の失敗も見る（11-07 の唯一の flake、N18 もここにあった）。
- **CI の失敗の多くは基盤の失敗なので、先に除く**。11-07 の T9 では、Docker のインストール、Docker Hub の 502、cosign、Go のモジュールの取得の失敗が、テストの失敗よりずっと多かった。基盤の失敗を除いてから flake を見るほうが早い。
