## 問題

`docker compose down -v` が、自分のプロジェクトのものではない名前付きボリュームまで消していた。

- 2 つのプロジェクトが、同じ `name:` のボリューム（`external` 無し）を宣言していると、片方の `down -v` が、もう片方が作ったボリュームを消す。データは永久に失われる。
- 起きやすい場面: 同じリポジトリを複数の git worktree やディレクトリで動かす（compose.yaml の `name:` が同じになる）。`external: true` の書き忘れ。
- `up` のほうは「別のプロジェクトのもの」と警告して、そのまま使う（作り直しもしない）。`up` と `down` で扱いが食い違っていた。
- リリース版（5.0.1）でも再現した。

## 原因

- `pkg/compose/down.go` の `removeVolume` が、`VolumeInspect` を呼んでいるのに、その結果を捨てて、名前だけで消していた（`_, err := ...`）。
- ネットワークを消す `removeNetwork` は、プロジェクトのラベルで絞っている。`up` 側は、`observed_state.go` の `ownedConfigHash` で持ち主を確かめている。ボリュームの削除だけが、持ち主を見ていなかった。

## 修正内容

レビューの前後で、守るものの範囲が広がった。

- **最初の版**: ラベル `com.docker.compose.project` が**別のプロジェクト**を指していたら、消さずに飛ばす。
- **ndeloof の指摘 1（ラベルの無いボリューム）**: 「Compose は自分が作っていないボリュームを決して消さない」が PR の趣旨。プロジェクトのラベルが無いもの（Compose の外で作ったもの）も、持ち主が分からないので飛ばすべき。`up` もそれを unmanaged として扱っている。
  → 条件を `owner != projectName` にした。ラベルが別のプロジェクトでも、空でも飛ばす。警告の文面で 2 つを区別する（`Volume belongs to project "x"` / `Volume was not created by Docker Compose`）。
- **ndeloof の指摘 2（fail closed）**: inspect が NotFound 以外で失敗したとき、所有の確認をせずに消していた。
  → `failed to inspect volume <name>: <err>` を返し、ボリュームは残す。`removeNetwork` と同じく、`down` は失敗する。NotFound（すでに消えている）は、これまでどおり何もしない。
- **ndeloof の提案（e2e）**: 2 つのプロジェクトで同じ名前のボリュームを共有するシナリオを足した。

## 学び

- **守るものは一般化して書く**: 最初は「別のプロジェクトのもの」だけを守ったが、本当の趣旨は「Compose が作っていないものは消さない」だった。ラベルの無いボリュームも同じ理由で守るべきだった。
- **確かめられないときは、安全な側に倒す（fail closed）**: 持ち主を確かめる処理を足すなら、確かめられなかったときの扱いまで決める。データを消す操作では「消さない」が安全な側。
- **メンテナが実機で再現してくれた**: issue に再現手順を付けたので、レビューが「本当に起きるか」ではなく「どう直すか」から始まった。
