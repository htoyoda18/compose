## 問題

`depends_on` で `condition: service_healthy` か `service_completed_successfully` を指定していると、依存先がすでに条件を満たしていても、最初の確認まで必ず 500ms 待っていた。

- 何も変わらない `docker compose up -d` が、約 0.07 秒で終わるはずのところ約 0.6 秒かかる。
- `up -d --wait` は最後の確認でもう一度払うので、約 1.1 秒かかる。

## 原因

- `pkg/compose/service_containers.go` の `waitDependencyReached` のループが、500ms の `time.Ticker` を待ってから、最初の確認をしていた。2021 年からこの形。

## 修正内容

- `service_healthy` と `service_completed_successfully` は、待ちに入った直後に 1 回確かめる。満たしていれば、tick を待たずに抜ける。
- `running_or_healthy`（`up --wait` と、コンテナのラベルから組み立てたプロジェクトの依存で使う）は、これまでどおり最初の tick の後に確かめる。
  - この条件は、healthcheck の無い running のコンテナを合格にする。起動直後に確かめると、すぐ終了するコンテナを「running」と判定してしまい、`--wait` が失敗として報告できなくなる。
- 書き方: ループを `for first := true; ; first = false` にして、最初の 1 回だけ `select`（ticker と `ctx.Done()`）を飛ばす。飛ばしても、その後の `if ctx.Err() != nil` は通る。

経緯:

- **最初の版（10-24）**: ループの前で 1 回確かめる形。context がすでに終わっていたら確かめないように、`ctx.Err() != nil` の条件を足していた。
- **ndeloof のコメント（10-26）**: LGTM。「副作用を考えたが見つからなかった。`check*` の関数は変えず、最初に呼ぶ時刻だけが変わる。`running_or_healthy` が tick を待つのも正しい」。そのうえで、#14376（`waitDependency` のループを作り変えた PR）がマージされて衝突したので rebase してほしい、との依頼。
  - 保つべきこととして、main では `select` の後に `if ctx.Err() != nil` があり、tick と `ctx.Done()` が同時に来ても、取り消された待ちでもう 1 回確かめないようになっている、と指摘された。解き方として「最初の 1 回は `select` を飛ばし、同じ `ctx.Err()` の判定に落とせばよい」と提案された。
  → 提案どおりに rebase した。自分で足していた `ctx.Err() != nil` の条件は要らなくなった。自分で足したコメントも減らした。
- **CI での失敗（10-26）**: e2e の `TestUpWithDependencyExit` が落ちた。この e2e は、healthcheck の無い依存先が、すぐに `exit 1` する。最初の確認が早くなったので、終了より先に確かめることが増え、`exited (1)` ではなく `has no healthcheck configured` を報告していた。`up` が失敗することは変わらず、メッセージだけが違う。
  → テストの趣旨は「healthy になる前に終了する」なので、testdata の `db` に healthcheck を足した。これでタイミングにかかわらず `exited (1)` になる。
- **ndeloof の CHANGES_REQUESTED（10-27）**: 既存の `TestExecutePlanCanceledCallerReportsNothingMore`（`pkg/compose/executor_start_test.go`）が不安定になった。`-race`、`GOMAXPROCS=2` で、main では 150 回中 0 回、このブランチでは 300 回中 20 回失敗する。
  - このテストは、待ちの最初の `ContainerInspect` の中で、呼び出し元の context を取り消す。修正前は、その inspect が 500ms の後だったので、`api` の起動のノードはとっくに依存の `select` で止まっていて、`ctx.Done()` で起こされていた。修正後は inspect が待ちの入り口で起きるので、`api` のゴルーチンが `select` に着く前に取り消しが届くことがある。すると `done` と `ctx.Done()` が両方とも準備済みになり、`select` がどちらかを無作為に選び、取り消しの後に `Starting` のイベントを出してしまう。テストが、言わずにこのタイミングに頼っていた。
  - `runNode` 自体の競合はこの PR が持ち込んだものではなく、ndeloof が別に直すとのこと。この PR では、テストがスケジューリングに頼らないようにすればよい。直し方も提案された: `synctest.Test` の中で動かし、mock の inspect をチャネルで止め、`synctest.Wait()` で `api` のノードが依存で止まるのを待ってから `cancel()` し、inspect を進める。`-race -count=300`、`GOMAXPROCS=2` で確かめること。
  → 提案どおりに直した。再インデントが多いので、レビューしやすいように別のコミットにした（「マージ前に squash してもよい」と添えた）。600 回中 600 回通る（直す前は 300 回中 28 回失敗）。
- 10-27 に APPROVED、マージ。

## 学び

- **タイミングを変える修正は、そのタイミングに頼っていたテストを壊す**: 単体テスト（`TestExecutePlanCanceledCallerReportsNothingMore`）と e2e（`TestUpWithDependencyExit`）の 2 つが、500ms 待つことに言わずに頼っていた。どちらも手元の実行では気付かず、e2e は CI で、単体テストはメンテナの繰り返しの実行で見つかった。
  - 出す前に、関係するテストを `GOMAXPROCS=2 go test ./pkg/compose/ -race -count=300 -run ...` で流しておけば見つかった。
  - 古いタイミングを前提にしたコメント（「500ms」「never on entry」）や、短い timeout（50ms）のテストを grep すれば、影響する場所の目星が付いた。
- **同じ関数を変える PR が先にマージされたら、その PR が足した約束を保って rebase する**: 本文に #14376 との重なりを書いていたので、メンテナが衝突の解き方まで示してくれた。
- **テストは時刻ではなく `synctest` で決定的にする**: `synctest.Test` で最初の確認の時刻を固定したテストは、レビューで評価された（「thanks ... for locking the first-check timing in a test」）。同じ道具で、不安定になったテストも直せた。
- **再インデントの多い変更は、別のコミットに分ける**: 差分を読みやすくするため。
