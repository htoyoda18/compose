## 問題

Docker Desktop の `desktop-linux` など、default 以外の context で `docker buildx use X`（`--global` なし）や `docker buildx create --use` で選んだ builder を、`docker compose build` が使わない。
さらに、ビルドのたびに buildx の選択が消え、その後の `docker buildx build` も既定の builder に戻る。v2.39.3 から（5.0.1 と main で同じ）。

Docker Build Cloud の公式の手順（`docker buildx use cloud-...` → `docker compose build`）も、同じ仕組みで壊れる（Build Cloud そのものでは未確認）。

## 原因

- `shellout.go` の `propagateDockerEndpoint` が、buildx を呼ぶときに、`DOCKER_CONTEXT` と一緒に `DOCKER_HOST` を必ず渡す。
- docker CLI は `DOCKER_HOST` があると "default" の context を選ぶ。buildx は、選んだ builder を context の名前をキーに保存しているので、キーが合わずに選択を消してしまう。
- この箇所は往復している: #12961（常に渡す）→ TLS の context が壊れた #13015 → #13007（条件付き）→ リモートでビルドできない #13134 → #13182（常に渡すに戻す）→ 今回の不具合。

## 修正内容

- 現在の context が `command.DefaultContextName` でなければ、`DOCKER_CONTEXT`（と `USER_AGENT`）だけを渡す。名前付き context は endpoint と TLS の情報を自分で持っていて、子の CLI プラグインは名前で解決する。buildx の builder の選択のような context ごとの状態も、名前で引かれる。
- default の context（`-H` / `DOCKER_HOST` のときも含む）は、これまでどおり `DOCKER_HOST` と TLS の情報を渡す。
- 2 コミット目（11-04）: agammann の指摘「親から `DOCKER_HOST` を引き継ぐと、名前付き context が負ける」への対応。
