# PR #14154: fix(down): spare dangling images of orphaned services, like their tagged image

https://github.com/docker/compose/pull/14154

## 問題

`down --rmi` は、プロジェクトの過去のローカルビルドで残ったdangling（untagged）
イメージを一切掃除してこなかった。`pkg/compose/image_pruner.go` の
`labeledLocalImages` にはこれを示す `// TODO(milas): we should really clean up
the dangling images as well (historically we have NOT); ...` というコメントが
残っており、「CLIの進捗出力に意味の無い生のimage IDを並べても分かりにくい」
という理由で意図的に未対応のまま放置されていた。

## 原因

最初のバージョン（レビュー前）では、プロジェクトのdangling imageを条件なしに
全て削除する実装にしていた。しかしレビュー指摘で不整合が発覚:

- タグ付きイメージ側の削除ロジック（`ImagesToPrune`）は、既に「serviceが
  現在のプロジェクトモデルに存在しない（＝orphan）場合、`--remove-orphans`
  が指定されない限りそのイメージを保持する」というチェックを行っている。
- 一方、dangling image側にはそのチェックが無かった。

そのため、orphanなserviceを含むプロジェクトで `down --rmi local` を実行すると、
そのserviceのタグ付きイメージは保持されるのに、同じserviceのdangling image
だけは削除されてしまう、というコマンド内で結果が矛盾する状態になっていた。

## 修正内容

- `down.go` と `watch.go`（`pruneDanglingImagesOnRebuild`）がそれぞれ個別に
  部分的・divergentに実装していた「プロジェクトのdangling imageを列挙し、
  `keep` 述語で除外されなかったものを削除、個々の失敗は許容する」という
  ロジックを、`composeService.removeDanglingImages`（`image_pruner.go`）
  という共通ヘルパーに統合。他の一括削除処理と同様に `errgroup` で並列化。
- `down.go` の `keep` は `ImagesToPrune` 自身の
  `RemoveOrphans`/`project.GetService` チェックを再現するようにし、
  タグ付き・dangling両方のイメージで保持/削除判定が一致するようにした。
- `watch.go` の `pruneDanglingImagesOnRebuild` は、既存の「直近ビルドで
  作られたimage ID」チェックを `keep` として同じヘルパーに渡すだけに簡素化
  （挙動は変えず、重複コードのみ解消）。
- `down` 側では削除結果を「Dangling images」という1つのグループ化された
  イベントとして報告するようにし、生のimage IDを1行ずつ出力しないようにした
  （TODOコメントが懸念していたCLI出力の煩雑さの解消）。
- `image_pruner.go` に残っていた上記TODOコメント自体を削除。
